# Catalina startup diagnosis (before fixes)

Target requested: macOS Catalina 10.15.8, Intel x86_64. No real Catalina device is available in this Linux environment. Record `sw_vers` on the target: the reported version must be checked rather than assumed.

## 1. Tauri Dev protocol panic

Confirmed from published dependency source, not a macOS runtime reproduction:

- Reported tauri-runtime-wry 2.12.4 depends on wry ^0.57.0 and tao ^0.37.0. Wry 0.57.0 unconditionally declares `webView:navigationAction:didBecomeDownload:` and the corresponding response selector in `src/wkwebview/class/wry_navigation_delegate.rs`.
- These WKDownload delegate callbacks require macOS 11.3+, absent from Catalina's runtime protocol metadata. The older downloaded Wry 0.51.2 also declares these selectors; blindly downgrading is not justified.
- objc2 0.6.5 `src/__macro_helpers/define_class.rs`, `ClassProtocolMethodsBuilder::add_method`, panics on a selector missing from the runtime protocol when compiled with `debug_assertions`. This exactly matches the supplied error. This is class registration, before any download occurs. Tao's event loop is not the source of this selector registration.
- Changing the deployment target or the bundle minimumSystemVersion does not add WebKit APIs to Catalina. Release omits this particular assertion; that does not establish overall compatibility.
- The current checkout resolves tauri 2.5.1 / runtime-wry 2.6.0 / wry 0.51.2 from an ignored workspace lock. These differ from the user's failing graph; no claim of reproducing that exact graph is made.

Minimal project workaround to verify: a separate opt-in dev profile with `debug-assertions = false` for package objc2 only. Keep application assertions enabled. This reduces Rust library diagnostics, not macOS security. It is not an upstream runtime-availability fix and does not certify other WebKit calls. No dependency update is needed.

Sources: crates.io source archives for tauri-runtime-wry 2.12.4, wry 0.57.0 and objc2 0.6.5; Apple's WKNavigationDelegate download callback availability. Confirm the actual Wry version with `cargo tree --target x86_64-apple-darwin` on the target.

## 2. React ErrorFallback

Confirmed: src/App.jsx catches descendant render/lifecycle exceptions but only prints error and errorInfo to the JavaScript console. The fallback recommends F12; that does not provide diagnostics on the reported device.

Unconfirmed: the actual exception and affected component, whether caused by old JavaScript/WebKit APIs, settings, a provider, or another application defect. A release build succeeding proves none of these. No speculative frontend compatibility fix is warranted yet.

Plan: bounded local JSON containing message, JS stack and React component stack, enabled only with an explicit process environment flag; fixed private destination, no remote upload or arbitrary write path. Generic fallback by default, user may explicitly reveal report location/status. Also handle/report an unavailable IPC transport without breaking the fallback.

## 3. Finder startup / persistence

Confirmed in source: constants CONFIG_PATH and LOG_PATH use current_dir. setup_app_state constructs metadata/settings/search state before Logger::init. SettingsState default write failure calls log_error; Logger::global's OnceCell initializer creates SettingsState::new again. A repeated write failure recursively enters that same OnceCell and waits. This matches the supplied sample but the supplied sample file itself was not available for independent inspection.

Plan: initialize platform app config/log paths from Tauri's resolver before creating state; bootstrap logger from in-memory defaults with no settings I/O, then attach the real shared settings. Use an explicit non-destructive legacy settings import, never trust arbitrary Finder cwd as a migration source. Rebase serialized abs_file_path_buf when loading settings. Preserve old files and existing destination settings. Templates require an explicit documented copy; metadata is regenerated by existing behavior.

Remaining hypotheses: exact Finder working directory and permissions on the target; other startup errors after the deadlock is removed. Test an unwritable settings destination in a subprocess with a timeout, migration/no-overwrite behavior, and non-project working directory startup on the target.

## Implemented scope

The opt-in `catalina-dev` profile avoids the objc2 debug-only registration assertion without changing dependency versions. Native behavior remains unverified. Startup resolves paths through Tauri before creating application state. The bootstrap logger no longer performs settings I/O and later attaches the real settings. An explicit EXPLR_LEGACY_CONFIG_DIR import preserves old/new user files and rebases the serialized save path. EXPLR_DIAGNOSTICS=1 enables a bounded private frontend JSON report; ordinary production fallback contains no exception text.

The old eager `expect` argument logged a critical startup message even on success; it also accessed the logger before the new setup hook. It was replaced with explicit error handling so no logger/path access precedes path initialization.

Regression evidence and limits are recorded in [validation-results.md](validation-results.md). Device instructions are in [catalina-verification.md](catalina-verification.md). No file-manager operations, dependency versions, macOS security settings or system libraries were changed.

Availability cross-check: the Apple SDK WKNavigationDelegate header (macOS 11.3 SDK, [public SDK mirror](https://github.com/phracker/MacOSX-SDKs/blob/master/MacOSX11.3.sdk/System/Library/Frameworks/WebKit.framework/Versions/A/Headers/WKNavigationDelegate.h#L179)) explicitly annotates both didBecomeDownload callbacks with `API_AVAILABLE(macos(11.3), ios(14.5))`. This confirms the API boundary independently of the supplied stack. Published source: [Wry 0.57.0](https://docs.rs/crate/wry/0.57.0/source/src/wkwebview/class/wry_navigation_delegate.rs), [objc2 0.6.5](https://docs.rs/crate/objc2/0.6.5/source/src/__macro_helpers/define_class.rs).
